# Status Check

Вебзастосунок для відстеження дедлайнів і комітментів, наданих спеціалістами різних відділів та проєктів. Поєднує спільний календар і базовий таск-трекер, у якому задачі передбачають **контроль виконання іншою людиною**, а не виконання дії самостійно.

🔗 **Живе демо:** https://taras0520.github.io/status-check/
---

## Що це і яку задачу вирішує

«Status Check» дає командам спільний календар, у якому можна фіксувати комітменти (зобовʼязання) з дедлайнами та призначати відповідального за їх перевірку. Система сама стежить за дедлайнами: якщо комітмент не закрили й не перенесли вчасно, він автоматично переходить у статус `expired`, а відповідальний за перевірку отримує сповіщення в Telegram.

## Стек

- **n8n** — бекенд-шар: REST API через вебхуки + фонова автоматизація статусів за розкладом (cron).
- **Supabase (PostgreSQL)** — спільна база даних з enum-контролем статусів і звʼязками між таблицями.
- **FullCalendar** — фронтенд-календар (однофайловий HTML, без збірки).
- **Telegram Bot API** — сповіщення відповідальному за перевірку.

## Архітектура

```
Браузер (HTML + FullCalendar)
        │  POST /webhook/status-check  (action: create | list | update | delete)
        ▼
n8n  ──  Webhook → Switch(action) → Postgres-нода → Respond
        │
        └─ Schedule (щогодини) → PG Expire → IF → Telegram
        ▼
Supabase (PostgreSQL)
```

Бекенд побудований на **одному вебхуці** з маршрутизацією по полю `action` — повний CRUD через єдину точку входу. Окремий cron-воркфлоу раз на годину переводить прострочені комітменти у `expired` і сповіщає рев'юера.

## Функціонал

- Спільна база-календар, картки розставляються за полем «дедлайн»
- Створення, редагування, зміна статусу та видалення комітментів
- Статуси з кольоровим кодуванням: `to check`, `expired`, `done`, `not actual`, `ideas backlog`
- Автоматичний перехід `to check → expired` при простроченні дедлайну (cron)
- Telegram-сповіщення відповідальному за перевірку про прострочені комітменти
- Фільтри за проєктом і за відповідальним за перевірку
- Підтримка дедлайну як з конкретним часом, так і «лише дата» (all-day)

## Поля комітменту

| Поле | Опис |
|---|---|
| Автор | хто створив комітмент |
| Title | назва |
| Опис | деталі |
| Дата створення | проставляється автоматично |
| Проєкт | для фільтрації |
| Відповідальний виконавець | хто виконує (може бути зовнішнім) |
| Відповідальний за перевірку | хто контролює (отримує сповіщення) |
| Дедлайн | дата або дата+час |

## Технічні рішення

- **Параметризовані SQL-запити** (`$1, $2…`) — захист від SQL-ін'єкцій.
- **`COALESCE` в UPDATE** — часткове оновлення: оновлюються лише передані поля, решта лишається без змін.
- **`NULLIF(...)` + явне приведення типів** (`::uuid`, `::timestamptz`, `::commitment_status`) — коректна обробка порожніх полів і enum/uuid/timestamp значень.
- **Фільтри через `IS NULL OR`** — один запит покриває і «всі записи», і фільтрацію за конкретним значенням.
- **`is_all_day`** — прапорець для рендеру картки як події на весь день або з конкретним часом.

## Як протестувати

1. Відкрий живе демо за посиланням вище.
2. Натисни **+ Комітмент**.
3. Заповни Title і Проєкт (обовʼязкові), задай дедлайн.
4. У поля **Автор** і **Рев'юер** встав UUID тестового користувача:
   ```
   e457a253-69b2-4d83-95b9-7f590aecdd45
   ```
5. Збережи — картка зʼявиться в календарі кольором за статусом.
6. Клік по картці — редагування, зміна статусу або видалення.
7. Кнопка **Оновити** підтягує свіжі статуси з бази (зокрема ті, що cron перевів у `expired`).

## Структура репозиторію

- `index.html` — фронтенд (FullCalendar + логіка запитів до API)
- `status_check_n8n.json` — експорт воркфлоу n8n (API + cron)
- `status_check_schema.sql` — схема бази даних для Supabase/PostgreSQL
